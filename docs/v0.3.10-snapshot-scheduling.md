# v0.3.10 L2 快照调度优化说明（2026-08-23）

## 结论

生产窗口 `2026-08-22 02:08:08--18:35:00 UTC` 内，837 次 transport recovery 平均 5.562 秒、
最长 17.387 秒；557 次 L2 reanchor 平均 32.837 秒、最长 115.571 秒。队列平均 2.13%、峰值
4.5%，event-loop lag 平均 0.293 秒、峰值 1.172 秒，且无 OOM 或进程重启。因此 L2 的固定长尾
不能归因于 writer 或内存耗尽，直接原因是全局 snapshot lock 覆盖了限速等待和完整 HTTP I/O：
任意一个慢 REST 请求都会阻塞后续全部 symbol。

v0.3.10 在 v0.3.8 的真实消息率加权路由、三次 audit 门禁、两次定向恢复门禁、连接 generation
隔离和指数退避以及 v0.3.9 的横截面选币规则之上，仅替换 REST snapshot 调度。它不改变正式
60 币、universe 身份、raw schema、gap 语义、rsync/ACK 或 107 central。

## 调度规则

- snapshot 只在全局限速锁内预约请求起点，随后释放锁再执行 HTTP；请求起点至少相隔 0.75 秒；
- 使用容量为 4 的共享 semaphore 限制慢 snapshot HTTP，避免恢复风暴无限占用 socket 和内存；
- snapshot waiter 包含等待 semaphore、等待时间槽和正在执行 HTTP 的请求；只要 waiter 非零，低优先级
  discovery、kline 和 retry REST 就等待；
- waiter 在成功、HTTP 异常或任务取消时均由 `finally` 递减，最后一个 waiter 离开后恢复后台 REST；
- `limit=1000` 的 depth snapshot 权重为 20，0.75 秒间隔对应约 1,600 weight/min；部署时
  `/fapi/v1/exchangeInfo` 报告 IP 限额为 2,400 weight/min，余量留给 OI 和低频控制请求；
- 单 route 含约 15--17 个需要 snapshot 的 symbol，单路由恢复时最后一个请求的纯调度等待约
  10.5--12 秒，测试门槛为不超过 13 秒；冷启动时 4 个 route 共享同一个全局限速器，60 个请求的
  纯调度等待上界为 44.25 秒，测试门槛为不超过 45 秒。HTTP 自身尾延迟不计入这些排队上界。

## 模块边界与轮询

- `collector/rest.py` 只负责 HTTP 请求与 recovery snapshot 优先级，不依赖 WebSocket route；
- `collector/scheduling.py` 提供固定周期推进和有界错峰，避免 polling loop 各自实现时间算法；
- `collector/readiness.py` 分开 realtime 和 discovery 两个 phase，`sources.py` 只汇集 readiness 信号；
- `collector/sharding.py` 封装基于 message rate 的稳定分片纯算法，不依赖连接、REST 或生命周期状态；
- `collector/service.py` 只编排生命周期：已有 `formal-start.json` 时在 realtime ready 后立即关闭恢复
  gap；全新实验仍等待 discovery ready 后才写 formal start；
- 60 个 OI 的首轮请求在 5 秒内均匀错峰，后续仍按每币 30 秒固定周期执行，不增加稳态请求率。

实测全新状态完成 35 日 Kline 与 depth evidence 约需 6 分 24 秒；该工作继续在后台完成，但不能
再延长正式采集重启的全局 gap。

## 完整性边界

调度优化不能缩短或隐藏真实缺口。transport 仍需订阅 ACK 和首事件证明才关闭；每个 symbol 的 L2
仍需 snapshot bridge 且满足官方 `U <= lastUpdateId <= u` 才恢复 `VALID`。`pu/u` 不连续、HTTP
失败或重连等待期间，gap 必须保持 OPEN。后台 REST 的优先级只影响控制证据何时请求，不改变已经收到
的 raw 字节，也不能越过 snapshot readiness。

## 1C1G 资源合同

容器使用 1.00 vCPU、768MiB RAM、256 PIDs、64MiB ingest queue 和 WebSocket queue 16。增加的
并发最多保留 4 个约 1,000 档 JSON response；相对现有 Arrow 与 writer 内存预算很小。CPU 配额从
0.90 调整为 1.00 是为了使用实例完整的一核，避免人为 cgroup throttle 放大控制响应延迟；内存和
磁盘保护不变。

systemd unit 把 Compose 在受控 `systemctl stop` 时返回的 `130` 声明为成功；这只消除正常升级时的
假 `failed`/OnFailure 报警，collector 的异常退出码 `1`、OOM `137` 和真实 source failure 仍保持
失败并由 restart/alert 处理。

## 验收

发布前必须通过：

1. 慢 HTTP 并发测试，证明请求起点错开但 HTTP I/O 不串行；
2. 并发上限测试，证明任意时刻 snapshot HTTP 不超过 4；
3. 优先级测试，证明恢复 waiter 清空前不会启动后台 REST；
4. audit 回归，证明一次 audit 丢响应、下一次成功不会断开 route；
5. 完整 pytest、Ruff、mypy、Docker build 和正式 60 币的 1C1G 受限收包测试。

生产部署只执行一次受控重启并保留全部状态。上线后检查 route assignment 未变化、open gap 回到 0、
ACK 继续推进、无 OOM/restart。单 route 稳态恢复重点观察 L2 reanchor p95 小于 15 秒且最大值小于
30 秒；完整冷启动允许全部 realtime readiness 在约 45--50 秒内完成。外部 REST 持续超时可能突破
目标，此时 gap 应保持显式，不能通过调整有效性规则伪造达标。
