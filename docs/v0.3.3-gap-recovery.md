# v0.3.3 数据缺口与订阅恢复说明（2026-08-17）

调研日期：2026-08-17（Asia/Shanghai）。协议结论只引用 Binance 官方文档、Binance
官方 connector、`websockets` 官方文档和 Python 标准库文档；实现结论以仓库的
`v0.3.2`（commit `37f7175`）为基线。生产事件来自本次运维检查中保存的 Vultr 日志摘要，
不能代替完整 gap ledger 清点。

## 结论

`v0.3.2` 已经做到 loss-explicit：断线、sequence discontinuity、collector restart 都会留下
持久 gap，L2 也不会在 snapshot bridge 前恢复 `VALID`。`open-gaps=0` 只表示当前没有仍未关闭的
gap，**不表示历史数据没有缺口**；历史 WebSocket gap 内没有收到的原始事件通常无法补回。

当前最重要的采集器 bug 是 targeted subscription refresh 的故障域失控：单个
`(stream, symbol)` 的刷新 ACK、snapshot 或首条新事件失败，最多等待 180 秒后会从
`liveness_loop()` 抛出异常；`BinanceSourceGroup._run()` 使用默认的 `asyncio.gather()`，于是整个
source group 结束。`EdgeService` 通常在下一次 5 秒 storage check 发现它失败，随后停止全部 60 币、
写 `COLLECTOR_STOPPED_GAP` 并退出，最后由 systemd 重启。一次局部异常因而变成所有路由和 REST
poller 的全局缺口。

另有一个 scoped-gap 漏洞：当前 refresh 以 symbol 为单位。只检测到 public `depth` 静默时也会
同时重订阅该 symbol 的 `bookTicker`；只检测到 `markPrice` 静默时也会同时重订阅该 symbol 的
`aggTrade` 和 `forceOrder`。代码却只为最初 stale 的 stream 开 gap，因此健康 stream 在
`UNSUBSCRIBE/SUBSCRIBE` 切换期间可能丢事件而没有对应 gap。

v0.3.3 应把刷新失败收敛在单条 route 内，并把刷新范围缩到准确的 stale subscription。若准确刷新
失败或控制状态不再可信，应关闭并重建该 route；重建主动影响的所有 symbol/stream 都必须有显式
gap。routine 网络、ACK、audit 和 snapshot 故障不应终止整个 collector。

### 无法由 v0.3.3 倒推修复的历史数据

- `depth` gap 内的盘口演化不能由 gap 结束后的 REST snapshot 倒推出；snapshot 只能重新建立之后的
  权威状态。central 必须继续把 snapshot bridge 以前标为无效。
- `bookTicker`、`markPrice`、`aggTrade` 和 `forceOrder` 在 WebSocket gap 内没有收到的消息无法由
  当前采集器恢复。gap ledger 用于排除或量化这些区间，不是事件备份。
- Binance 官方把 `aggTrade` 定义为同一 taker order 在 100 ms 内的聚合，且不包含 insurance fund
  和 ADL trades；它本来就不是逐笔成交源。
- Binance 官方 `forceOrder` 每个 symbol 每 1000 ms 最多推送该窗口内最新一笔强平，无强平时不
  推送。即使网络完全正常，它也不是完整逐笔强平日志。
- `openInterest` 是项目每 30 秒的 REST sample，不是每次持仓变化的事件流。

因此，质量报告应同时给出 `explicit_invalid_ns`、`unclassified_ns` 和有效覆盖率；不能用
“gap 已 CLOSED”或“当前 open gap 为 0”表达历史完整。

## Binance 与客户端协议事实

### 连接、ping/pong 与消息静默

Binance USD-M Futures 官方 Connect 文档规定：连接预期在 24 小时后断开；服务端每三分钟发送
Ping，十分钟内没有收到对应 Pong 会断开；每个连接最多 1024 个 stream，client-to-server 消息
最多 10 条/秒。项目提前在 23 小时轮换且每路最多约几十个订阅，未接近这些上限。

项目将 `ping_interval=20`、`ping_timeout=20` 传给 `websockets.connect()`。
`websockets` 官方文档说明，这会每 20 秒发送 Ping，并在 20 秒内没有 Pong 时终止连接。因此它是
connection heartbeat，不是逐 subscription 的交付证明。协议层 ping 正常、连接仍有其他市场消息，
都不能证明某个 `(stream, symbol)` 没有静默丢失。

同理，`depth@100ms` 的 100 ms 是有 order-book update 时的推送速度，`bookTicker` 只在最优
bid/ask 价格或数量变化时推送；两者都不是 Binance 承诺的逐 symbol 心跳。当前对高流动性正式集合
采用 30 秒 liveness 是项目的保守质量策略，可能产生 false positive，但 false positive 应只引起
小范围、完整记账的恢复，不能升级为全局停机。

`markPrice@1s` 则由官方定义为每秒推送，因而 5 秒 deadline 是更强的逐 symbol liveness 证据。

### subscription ACK 与 audit 能证明什么

官方 live subscription API 定义：

- 成功的 `SUBSCRIBE` / `UNSUBSCRIBE` 以相同 request `id` 返回 `result: null`；
- `LIST_SUBSCRIPTIONS` 返回该连接当前订阅名称列表；
- 官方没有给这些控制响应规定一个固定响应时限。

因此 ACK 只证明控制请求被接受，LIST 只证明服务端控制面声明的当前集合。两者都不证明 ACK 之前
没有丢事件，也不证明每个订阅的数据面已经重新推送。项目要求 refresh 后等待对应 stream 的第一条
新事件，以及 depth 等待新 snapshot/sequence bridge，是必要的本地完整性政策。10 秒 audit timeout
和 180 秒 refresh timeout 也都是本地 policy，不是 Binance SLA。

## v0.3.2 故障链路

1. `RouteRunner.liveness_loop()` 以 `(stream_type, symbol)` 发现 stale，并以最后成功事件时间作为
   `affected_from_realtime_ns` 打开 scoped `CONNECTION_LOST_GAP`。
2. `_refresh_symbols()` 对所有 stale symbols 调用 `subscriptions_for(symbols)`；这会生成这些 symbols
   的所有 route subscriptions，而不是准确的 stale subscriptions。
3. WebSocket 连续发送 `UNSUBSCRIBE` 和 `SUBSCRIBE`。`SubscriptionUpdate.completion` 只有在两个 ACK
   都到达且所需 snapshot 全部成功后才完成；ACK 和 snapshot 没有独立 deadline。
4. 有 update pending 时，60 秒 subscription audit 被跳过。若一个 update ACK 消失但连接继续收市场
   数据，连接本身不会在 10 秒 audit deadline 失败；外层会一直等满 180 秒。
5. 180 秒超时、连接中途关闭或 snapshot task 失败会从 `liveness_loop()` 重新抛出。
6. `asyncio.gather(*routes)` 使用默认 `return_exceptions=False`，首个异常传播并结束 source group；
   storage loop 随后把它升级为 collector failure。

这解释了生产中的三次 180 秒后全局重启。它不是 Binance 要求，也不是保持完整性所必需；关闭有
歧义的单条连接并按 route 重订阅，能够获得更强证据且显著缩小缺口范围。

## v0.3.3 修复方案

### 1. 准确刷新，不干扰健康 stream

- liveness recovery API 接收 stale `(stream_type, symbol)` keys，而不是只有 symbols。
- `depth` 只重订阅 `depth@100ms` 并抓该 symbol 的 depth snapshot；`bookTicker` 只重订阅
  `bookTicker`；`markPrice` 只重订阅 `markPrice@1s`。
- 不因 `markPrice` stale 顺带切换 `aggTrade` / `forceOrder`，也不因 `depth` stale 顺带切换
  `bookTicker`。
- scoped gap 从该 key 最后一次可信事件开始，只有准确 subscription ACK、该 key 首条新事件，以及
  depth 的 snapshot capture 完成后才 CLOSED。central 仍需独立验证 snapshot bridge 才能恢复 L2
  `VALID`。

### 2. 将控制 ACK 与 snapshot deadline 分离

- 每个 pending `SUBSCRIBE` / `UNSUBSCRIBE` request 保存 monotonic deadline；不得只依赖外层 180 秒
  aggregate timeout。
- 控制 ACK timeout 使用版本化本地 policy（可复用当前 10 秒 control-response timeout），snapshot
  继续使用自身 HTTP timeout、有限 retry 和共享 2 秒 weight limiter。
- 任意 ACK 缺失、response `code`、LIST mismatch 或 pending state 不一致都使**当前 route
  connection** 失效；不在状态有歧义的连接上继续采集。
- 连接关闭时，所有 pending completion 必须恰好完成一次并清理；迟到 ACK、旧连接 completion 或被
  cancel 的 future 不得修改新连接的 desired subscription state。

### 3. route-local supervisor，不退出整个 source group

- targeted refresh 的可恢复异常不得逃逸并终止 `BinanceSourceGroup._run()`。
- refresh 精确重试失败后，liveness task 请求 `RouteRunner` 重建当前 route；不要持有
  `_update_lock` 等待重建，以免和午夜 universe update 死锁。
- 重建 route 会主动中断该 route 上其他健康 subscriptions，因此从停止旧连接前为该 route 的所有
  symbols/streams 打开 route-wide gap。新连接必须经过 initial ACK 和所有 liveness keys 的新事件后
  才关闭 transport gap；每个 L2 继续等自己的 snapshot bridge。
- 使用有上限的 backoff，并保证同一 route 同时最多一个 refresh/reconnect；连续失败保持 gap OPEN，
  不 busy-loop、不泄漏 task/future。
- 其他 public shards、market route、REST pollers、writers、ACK/GC 和 collector lease 继续运行。
  只有 writer durability、storage hard limit、进程 invariant 破坏等真正 process-wide 错误才退出服务。

### 4. 测试与部署验收

发布前至少覆盖：

1. 缺一个 refresh ACK：在 control deadline 后只重建该 route，其他 route/poller 不停止。
2. 两个 ACK 之间断线、LIST mismatch、snapshot 最终失败：gap 不提前关闭，且不会结束 source group。
3. 单独 depth/bookTicker/markPrice stale：发送的 remove/add 只含对应 subscription；健康 stream 不被
   切换。
4. route fallback reconnect：为被主动中断的全 route streams 打 gap；initial ACK + fresh events
   关闭 transport gap，但 L2 snapshot bridge 前保持无效。
5. 重复 timeout、第二次断线、service stop、并发 universe update：无 deadlock、busy-loop、orphan task、
   stale completion 或重复 gap close。
6. 1C1G soak：RSS 低于现有 768 MiB limit，queue ratio、event-loop lag、snapshot rate 和 ACK/GC
   持续正常。

部署必须保留 generation、formal-start、universe、ready、ACK、raw 和 open-gap state；只替换 pinned
image 并做一次受控重启。重启产生的 collector gap 必须保留。部署后至少确认：版本为 v0.3.3、60 币
和 universe hash 未变、所有 routes ready、open gaps 最终为 0、没有持续 refresh/audit error、107 ACK
继续推进，并在一个完整 UTC 日后重新计算历史 gap inventory 与 coverage。

## 未由资料证明的事项

- Binance 没有给 live-subscription ACK 固定 SLA；10 秒或其他 deadline 是本项目的恢复 policy。
- `no close frame received or sent` 不能单凭日志归因于 Binance、Vultr、网络路径或客户端。
- 30 秒 public liveness 不是 Binance delivery guarantee；它是宁可显式标 invalid 也不接受静默缺口的
  研究政策。
- 只有完整远端 gap artifacts 能给出历史 gap 的精确全集与总时长；当前 open-gap 目录和摘要日志均
  不足以单独证明历史覆盖率。
