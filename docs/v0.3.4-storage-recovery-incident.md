# v0.3.4 存储恢复事故复盘（2026-08-20）

## 结论

v0.3.3 的存储硬限制可以正确登记 `STORAGE_EXHAUSTED_GAP` 并暂停 sources，但 collector 在该 gap
仍为 OPEN 时重启，若磁盘空间已经恢复，启动流程会先启动并等待全部 Binance sources ready，随后
storage monitor 又调用一次 `SourceManager.start()`。第二次调用抛出
`RuntimeError: sources already running`，systemd 因此反复重启 collector。

v0.3.4 将 storage monitor 改为幂等状态协调：

- `hard_limited=true`：没有 storage gap 时先登记；sources 仍运行时停止；已有 gap 也必须保持停止；
- `hard_limited=false` 且存在 storage gap：仅在 sources 未运行时启动并等待 readiness；sources 已运行
  时不重复启动；最后关闭原 storage gap；
- 不删除或改写历史 gap，不把 crash loop 内缺失的 WebSocket 事件声明为完整。

## 生产证据

Vultr 在 `2026-08-19T16:09:01.932534298Z` 打开
`gap-6608039a4d5d46948407b32c6227091f`：

```text
reason=STORAGE_EXHAUSTED_GAP
spool_bytes=2086611550
free_bytes=5368217600
minimum_free_bytes=5368709120
```

这次保护触发是正确的：可用空间比 5 GiB 门槛少 491,520 bytes。collector 后续在该持久化 gap
仍为 OPEN 的情况下重启；从 `2026-08-19T16:27:33Z` 起，日志稳定出现：

```text
EdgeService._storage_loop -> SourceManager.start
RuntimeError: sources already running
```

截至修复前检查，systemd restart counter 已超过 400。每次重启后的短暂写入不能视为连续采集；
`STORAGE_EXHAUSTED_GAP` 与每次异常停止产生的 `COLLECTOR_STOPPED_GAP` 是数据完整性边界。

## 回归和部署要求

回归测试必须覆盖：

1. 已恢复 storage gap、空间可用且 sources 已运行时，不二次启动，只关闭 storage gap；
2. 已恢复 storage gap、空间仍不足且 sources 已运行时，必须停止 sources 并保持 gap OPEN。

升级只替换 Vultr edge image。必须保留 generation、formal-start、active universe、raw、ready、ACK、
day-index、lease 和全部 gap artifact。部署后要求：

- generation、60 币集合、`universe_hash` 和 formal-start 哈希不变；
- 所有 source route 达到 readiness；
- 遗留 storage/collector gap 自动产生对应 CLOSED artifact，当前 OPEN gap 回到 0；
- 至少两个 collector status 周期内无 `sources already running`，ready 与 ACK 持续推进；
- 107 不升级，继续使用现有 rsync pull 和 Slurm 处理。
