# v0.3.8 采集器可靠性优化记录

## 结论

2026-08-22 的生产证据表明，主要问题不是 writer、队列、磁盘或网卡丢包，而是 1C1G 主机在高消息率
route 上接近 CPU 上限后，把短暂的上游或链路抖动放大成重复审计超时、重连和串行 L2 重锚。
v0.3.8 保持正式 `7.0` 的 50 core、5 boundary、5 probe、raw schema、rsync 和 107 central 合同
不变，只优化 Vultr source lifecycle。

## 生产证据

部署前连续约 16 小时记录到 392 次连接失败：191 次 subscription audit timeout、138 次 ping
timeout、63 次无 close frame。`public-1` 占 294 次，明显高于 `public-2` 的 48 次、`public-3`
的 32 次和 `public-0` 的 15 次。transport 通常在 2.36 秒内恢复，最长 11.27 秒，但 L2 等待共享
串行 snapshot 的时间远长于 transport，最长 invalid window 约 52 分钟。

同一窗口内 queue 峰值仅约 4.5%，RSS 峰值约 436MiB，网卡无 RX/TX error 或 drop；容器 CPU
P95 接近 0.9 CPU 配额并持续出现 cgroup throttle，event-loop lag P95 约 0.83 秒。证据支持以下
因果链：外部抖动触发一次延迟，热点 route 与 CPU throttle 延迟控制响应，激进 deadline 随即重连，
每次重连又为整路触发 snapshot，进一步占用 event loop 和 REST 串行器。

## 正式规则

- public route 初次启动按每币生产消息率执行确定性最小负载分配；后续 universe revision 保留所有
  未变化成员的 route，只把新增成员放到当前估算负载最低的 route；
- `websocket_max_queue=16`，只增加有界协议缓冲，不改变 64MiB ingest queue；
- `mark_price_liveness_seconds=15`，避免 1 秒流的单次调度尖峰直接触发恢复；
- subscription audit 每 60 秒发起，单次等待 20 秒，连续 3 次无响应才重连；集合确实不一致仍立即
  fail closed；
- 定向 subscription refresh 连续 2 次失败才重连所属 route；失败结果必须属于当前活跃 connection
  generation，旧连接遗留 future 不能中断新连接；
- 连接异常使用带 jitter 的指数退避，约从 1 秒起步、30 秒封顶；稳定运行 60 秒后重置失败计数；
- 1,000 档 snapshot 的共享安全间隔从 2 秒降为 1 秒。每次权重 20，持续上限约 1,200
  weight/min，在部署时观测到的 2,400/min IP 限额下保留约一半给 OI、discovery、retry 和变化余量；
- day seal grace 调整为 150 秒，覆盖最坏的 60 秒 audit interval 加 3 次 20 秒 deadline，防止 gap
  proof 晚于前一日 inventory seal。

初始 message rate 取生产事故窗口和上线前最新完整一分钟样本中的高水位，是每分钟 public
消息数的路由容量估计，不是选币分数，也不会改变 core/boundary/probe 身份。未知的新币使用已知
rate 中位数，随后只在配置
发布时校准；运行中不会因为短期流量变化搬迁稳定成员。

## 完整性约束

任何容错阈值都不能隐藏数据缺口。第一次 stream silence 仍立即打开精确到 `(stream, symbol)` 的
gap；阈值只决定何时从定向恢复升级为 route reconnect。transport gap 仍需订阅 ACK 与新事件证明
后关闭，L2 仍需每币 snapshot bridge，`pu/u` 不连续仍立即产生 `L2_SEQUENCE_GAP`。指数退避期间
gap 保持 OPEN，不能把等待时间声明为有效数据。

## 验收

发布前必须通过完整 pytest、ruff、mypy、Docker build，以及 `cpus=0.90`、`mem_limit=768m` 的
1C1G 约束运行。部署只允许一次受控重启，并保留 raw、ready、writing、ACK、universe、gap、lease
和 formal-start。上线后至少观察 60 分钟：服务 active、无 OOM、open gap 回到 0、107 ACK 持续，
各 public route 消息负载接近，审计/刷新不再形成周期性重连风暴。

发布前实跑使用正式 60 币配置、`0.90 CPU`、`768MiB`、`256 PIDs` 和禁用 swap 的容器限制。
约 70 秒窗口内 RSS 从 119MiB 增至 165MiB，CPU 采样从 0.41 core 增至 0.82 core，PID 为 8；
期间接收约 63MiB 网络数据并持续生成三类 ready chunk，无 OOM、无容器退出。该结果只证明上线前
容量与真实收包路径，最终可靠性结论仍以上线后的 60 分钟生产观察为准。
