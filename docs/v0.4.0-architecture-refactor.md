# v0.4.0 架构重构发布说明（2026-08-23）

## 兼容性边界

v0.4.0 删除旧 Python 包、旧模块路径，以及 `EdgeConfig`、`EdgeService`、
`CentralConfig`、`CentralPuller` 等公开符号。唯一一代 Python 数据模型也删除无意义的 `V1/_v1`
后缀；`GapEvent` 只接受当前 schema 2，不再保留 schema 1 解析分支。这是源码和 Python API 的
破坏性变更，因此版本从 v0.3.10 提升到 v0.4.0，不提供 import alias 或运行时兼容层。CLI、环境
变量、systemd unit、容器路径和部署目录也统一使用 `miry` 命名，旧运行接口被删除。

下列生产合同保持不变：

- raw/typed schema 与 chunk/day manifest；
- rsync ready、ACK 和 transfer ledger 协议；
- gap、formal-start 和 universe decision 内容；
- 107 `data/raw`、`data/derived` 和两端已有正式数据内容。

因此本版本采用保留状态的原地升级，只原子重命名 Vultr 数据根并更新路径引用，不执行 clean
start，不迁移或重写正式数据内容。

Python 名称去掉版本后缀不删除磁盘中的 `schema_version` 字段。raw、manifest、ACK、checkpoint 和
质量 marker 仍写原有数值/标识，以保持现有 v0.3 正式数据可继续拉取和处理；这里删除的是重复的
源码命名和已经过期的 gap schema 1 接受逻辑，不是改写历史文件。

## 新分层

源码根缩短为 `src/miry`。`collector` 负责 Vultr 实时采集，`pipeline` 负责 107 pull 与派生处理，
`universe` 提供可离线重放的纯选币规则，`contracts` 是两端共享合同，`cli` 只装配进程入口。
采集 sources 拆成 WebSocket routes、REST polling 和 orchestration；选币拆成 models、evidence 和
selection。依赖方向由 AST 测试约束，完整说明见 [架构与选币职责](architecture.md)。

## 稳定性修复

v0.4.0 同时修复运行期跨 route 搬币的空窗风险。旧实现会并发提交每条 route 的最终名单，源 route
可能在目标 route 完成订阅确认、snapshot 和首事件之前退订。新实现统一采用全局 add-ready-remove：
所有 public 目标 route、market route 和 OI poller 先扩容并完成各自 readiness，之后才统一裁剪；
扩容失败则不裁剪并回滚已成功的扩容。新增 symbol 的新鲜事件从更新发起时开始跟踪，因此 snapshot
尚未完成时到达的首事件也不会漏掉。

采集器保留 24 个完整小时的 public 消息峰值，每天 UTC 日切最多评估一次在线再均衡。证据不足、
目标分片不变时保持现状；需要搬迁时不重启 collector，不改变 universe 身份。长期 source 任务改由
结构化 `TaskGroup` 托管，任一 source 失败时其余任务会被取消并等待退出，不再遗留使用已关闭 HTTP
session 的孤儿任务。网络或 Binance 端断连仍可能发生，现有 transport/L2 gap 与 snapshot 恢复合同
继续负责显式记录和恢复。

## 升级验收

两端升级前记录 active universe 和 formal-start 哈希。107 先切换 SIF、`MIRY_*` 环境和 SSH
文件名并验证一次前台 pull，再恢复 cron；Vultr 后切换 immutable OCI digest 并执行一次受控重启。
验收要求：

- active universe、60 个成员和 formal-start 不变；
- collector 完成 realtime readiness，受控 stop gap 正常关闭；
- public route 每日再均衡日志为 evidence unavailable、assignment unchanged 或一次完整的
  `public routes rebalanced`，不得出现先退订造成的 gap；
- 107 `last-pull.json` 为 `state=ok` 且 `acks_pushed=acks_queued`；
- Vultr transfer status 无 hash mismatch、invalid ACK 或 pending transaction；
- ready、raw 和 transfer ledger 持续推进。
